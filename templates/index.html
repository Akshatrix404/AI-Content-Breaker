      Compiler-theory internals

      A second parsing algorithm, an IR with real optimizer passes, data-flow analysis, and a control-flow graph — all independently verified, not just tokenize/parse/score

      1 · Formal grammar verification — LL(1) table-driven parser

      The grammar parser.py uses (recursive descent) is formalized here as pure BNF, FIRST/FOLLOW sets are computed by the textbook fixed-point algorithm, an LL(1) parsing table is built from them, and a second, independent stack-based parser drives that table across the same sentences — used to cross-check the hand-written parser rather than trust a single implementation.

      2 · Intermediate representation — triples + optimizer passes

      Each sentence's parse tree is lowered into (subject, verb, object) and modifier triples, the same way a compiler lowers syntax trees to three-address code. Two classical optimizer passes then run over the whole document's IR stream: common subexpression elimination (an identical proposition seen twice) and dead-code elimination (a generic filler modifier with no discriminative content).

      3 · Data-flow analysis — reaching definitions

      A noun's first mention is a definition; a later pronoun is a use. The classic reaching-definitions worklist algorithm (GEN / KILL / IN / OUT, iterated to a fixed point) propagates definitions across sentences; a pronoun with no reaching definition is flagged the same way a compiler flags a use of an undefined variable.

      4 · Discourse control-flow graph — cyclomatic complexity

      Sentences are nodes; a mandatory sequential edge links each sentence to the next, and an extra "cohesion" edge is added whenever a later sentence reuses an entity from a non-adjacent earlier one (a long-range back-reference — structurally the same thing as a loop-back edge). McCabe's cyclomatic complexity M = E − N + 2P is computed over the resulting graph exactly as a static-analysis tool computes it for a function body.

      Every phase is deterministic and rule-based: a hand-written lexer and grammar, a recursive-descent parser, an attribute-grammar evaluator, and a fixed set of weighted formulas — no language model is used to detect or to judge. Humanizing is two-stage: fixed, named, logged rewrite rules first, then a local Ollama model (with RAG-retrieved human writing as style examples) proposes paraphrases that this same rule-based scorer accepts or rejects. No external API; the LLM never judges, the compiler-style scorer is the verifier.
